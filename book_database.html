PROJECT OVERVIEW

Project Scope

I built a SQL-first ELT pipeline that integrates book ratings and metadata from three structurally different datasets. Ordered migrations, transactional transformation, explicit rejection policies, and automated database tests make the normalized MySQL core inspectable and repeatable.

My contribution

DESIGN DECISIONS & TRADE-OFFS

Design Trade-offs

IDENTITY SCOPE

ISBN-10 edition as the core book grain

Decision

Only checksum-valid ISBN-10 editions enter the core. ASIN and malformed identifiers remain traceable in staging with reason codes.

Trade-off

Stronger referential integrity and honest entity grain at the cost of excluding valid ASIN-only interactions from the current core.

AMBIGUITY POLICY

Deterministic matching and conflict resolution

Decision

Title metadata is accepted only for a one-title-to-one-ISBN match. Repeated ratings keep the latest review date, then staging order; metadata uses explicit completeness and source precedence.

Trade-off

Prevents silent false joins and arbitrary selection, while deliberately leaving ambiguous or unmatched metadata unresolved.

REFRESH STRATEGY

Transactional full-core rebuild

Decision

The procedure rebuilds the normalized core from selected completed ingestion runs inside one transaction and records a failed transformation after rollback.

Trade-off

Simple replay, reconciliation, and failure recovery are prioritized over incremental or real-time updates.

FULL-DATA QUERY OPTIMIZATION

Query Performance

In the original full-data benchmark, the representative workload finds books positively rated by readers who also liked a selected title. EXPLAIN ANALYZE showed that the dominant bottleneck was repeated genre-view materialization—not the co-occurrence logic itself.

Query path Selected title → positive readers → co-rated titles → distinct-reader ranking → genre lookup

Before 12.9 s Runtime genre-view aggregation
→
After 2.8 s Indexed pre-aggregated lookup
78% shorter execution time
01

Diagnose the actual bottleneck

EXPLAIN ANALYZE exposed repeated materialization of v_canonical_book_genre, which processed more than 130,000 rows during each recommendation request.

02

Move repeated work out of runtime

Because MySQL has no native materialized views, the full-data implementation stored the genre aggregation in a refreshable physical table and indexed its canonical-title lookup.

03

Isolate and verify the improvement

The recommendation logic and result semantics stayed unchanged. Only the genre-serving layer was replaced, so the measured runtime difference isolates the effect of pre-aggregation.

Benchmark scope: these measurements come from the original full-data environment, not the tiny CI fixture. The comparison changes only the genre aggregation layer; the pre-aggregated table adds refresh and write cost in exchange for removing repeated work from the interactive query path.

SCOPE & LIMITATIONS

Limitations

Edition-level identity

The core represents valid ISBN-10 editions. It does not claim perfect work-level identity across editions, and ASIN-only interactions remain outside the current core.

Batch, not real time

The pipeline processes static source snapshots through audited staging runs and a transactional rebuild; it is not a streaming or distributed system.

Separate correctness and performance evidence

The CI fixture proves migration, integrity, failure, and repeatability behavior. The 78% optimization result belongs to the original full-data benchmark.

Next operational proof

Least-privilege role tests and a backup-and-restore smoke test are the next extensions beyond the current case-study scope.
